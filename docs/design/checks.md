# Реализация и визуальная приёмка PGS

## Где искать правило

Порядок подключения задаёт `src/app/layout.tsx`. В проекте остаются старые слои `globals`, `design-v3/v5/v6`, `design-atelier`; итоговый вид определяет их каскад с Monolith. Перед правкой проверяй computed style. Сначала исправляй ответственное правило, а не добавляй новый файл overrides.

| Область | Основной источник |
|---|---|
| Базовые поверхности, крупные блоки | `src/app/design-monolith.css` |
| Верхняя шапка, панели, поиск, состояния | `src/app/design-monolith-header.css` |
| Размеры текста и оси навигации | `src/app/design-monolith-typography.css` |
| Радиусы, исключения крупных блоков | `src/app/design-monolith-geometry.css` |
| Логотип | `src/app/brand-identity.css`, `public/brand/pgs-rhythm-letters.svg`, `pgs-rhythm-symbol.svg` |
| Контролы и таблицы | `src/app/design-monolith-system.css` |
| Интервалы и сетки рабочих разделов | `src/app/design-monolith-workspaces.css` |
| Общие страницы | `src/app/design-monolith-pages.css`, `design-monolith-dashboard.css` |
| Смысловые цвета | `src/app/design-monolith-semantic.css` |
| Латунные детали | `src/app/design-monolith-details.css` |

Не удаляй весь старый слой без карты его использования. Убирай конфликтующие переопределения в пределах задачи, сохраняя остальные разделы. Для нового общего свойства расширяй существующие переменные, а не заводи параллельную тему.

## Проверка по масштабу изменения

**Логотип, цвет, отдельный контрол:** текущий экран до/после; зависимые hover/open/focus; узкая ширина, если меняется размер. Проверка всех модулей не нужна.

**Макет раздела:** обычные и длинные данные, минимум один полный рабочий сценарий, узкий экран и desktop. Для таблицы проверь прокрутку, закреплённые колонки и действия.

**Общая типографика, сетка или навигация:** показательные страницы Обзор, График, Материалы, Документы, реестр проектов; затем остальные затронутые области. Используй контрольные ширины 320/390, 1024 и 1440px по релевантности, текущую пользовательскую ширину сохраняй для сравнения.

## Критерии

- Основные блоки имеют общие оси, а их интервалы видны и последовательны. Между KPI и следующим блоком нет случайного нулевого зазора.
- Длинная подпись не сдвигает числа соседних карточек. Числа и единицы выровнены согласованно; суммы в таблицах удобно сравнивать.
- Заголовок проекта, подписи и кнопки помещаются; многоточие применяется осмысленно. Проверяй ширину текста и реальный снимок, а не только `scrollWidth`.
- Нет горизонтального выхода всей страницы. В таблицах допустима явная горизонтальная прокрутка внутри контейнера; закреплённые действия не делают другие колонки недоступными.
- Меню открывается и закрывается, поиск появляется по клику, 3D доступен, фокус виден и возвращается корректно. Положение fixed-каталога не зависит от filter/transform предка.
- Контраст, ошибки, отключённые элементы, состояния загрузки и пустых данных остаются понятными. Масштаб проверки выбирай по затронутому поведению.
- Сравни исходный и итоговый снимки в одном просмотре при одинаковой ширине и состоянии. Повреждённый или не полностью загрузившийся снимок не является подтверждением качества.

Для изменений интерфейса проверяй соответствующий build/lint/typecheck и существующие тесты поведения по задаче. Для настройки навыка и документации проверяй ссылки, целостность файлов и работу инструкций; не запускай production build без изменения приложения.

Ни deploy, ни очистка данных не являются частью визуальной проверки. Действуй в рамках текущей задачи и уже данной авторизации; не добавляй повторные согласования, когда пользователь уже поручил публикацию.
