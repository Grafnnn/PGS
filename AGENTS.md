# PGS — правила работы с интерфейсом

Эти инструкции относятся к UI PGS. Следуй текущему запросу пользователя; небольшие изменения выполняй прямо в утверждённом дизайне.

## Актуальная версия

Продукт — PGS Studio, рабочая система управления строительством. Активная визуальная система — Monolith, логотип Rhythm.

На этой машине есть разные checkout, и их содержимое НЕ одинаково:
- `/Users/ag/Documents/PGS-monolith-release` — актуальный код опубликованного Monolith.
- `/Users/ag/Documents/PGS-atelier-current` — дизайн-лаборатория и локальное превью; содержит незакоммиченные эксперименты и референсы.
- `/Users/ag/Documents/PGS` — старый рабочий checkout, не эталон нового UI.

Перед изменением сверяй `git status`, ветку, историю и наличие активных CSS в `src/app/layout.tsx`. Снимок принятой базы: `732529e3`, 2026-09-09; это ориентир истории, не команда отката. Новейшая работа и явный выбор пользователя имеют приоритет. Не копируй checkout целиком и не затирай параллельные изменения. На другой машине определяй нужный checkout по Git и исходникам, а не по отсутствующим абсолютным путям.

## Дизайн

- Используй `$pgs-design`, если навык доступен. При его отсутствии достаточно документов ниже.
- Перед UI-работой читай [актуальный бриф](docs/design/brief.md). Для затронутой области выбирай релевантный [визуальный референс](docs/design/reference-library.md).
- При проектировании модулей читай [направления модулей](docs/design/module-direction.md). Макет отражает главную задачу: обзор — решения, график — время и зависимости, материалы — потребности и поставки.
- Для крупного редизайна создавай три визуально разных композиции на одинаковом сценарии. Если выбор делегирован тебе, выбери и обоснуй сам; если пользователь хочет выбрать, покажи варианты до реализации.
- Для точечных правок сохраняй остальное оформление и не запускай поиск концепций заново.
- Согласуй выбранное решение с актуальными данными и поведением. Изображения концепций и demo-данные не являются производственными данными.

## Реализация и проверка

- Источники стилей и критерии проверки — [checks.md](docs/design/checks.md). Изменяй правило в его основном слое; избегай очередного глобального CSS поверх конфликтующих тем.
- Используй имеющиеся компоненты, Lucide и ресурсы PGS. Подключай новые инструменты только под конкретную задачу.
- Проверяй изменения визуально в браузере и сравнивай до/после в одинаковом состоянии. Ширину и глубину проверок выбирай по масштабу изменения; для правки логотипа не нужно проходить все 26 модулей.
- Для кода выполняй проверки, относящиеся к изменению. Изменение только инструкций не требует пересборки приложения или деплоя.
- Готовый результат показывай со снимком, когда это помогает оценить дизайн. Указывай проверенные состояния и существенные ограничения.

## Инструменты

Product Design — для концепций и аудита; Image Generation — для визуальных направлений и оригинальных материалов; Figma — для редактируемых макетов при наличии заданного файла; браузер — для живой проверки. Не создавай обязательную зависимость от Figma, когда исходный код и браузер уже решают задачу.

При полезном распараллеливании выделяй конкретные задачи арт-директору, UX-проектировщику, разработчику и проверяющему. Это ИИ-роли; не изображай приглашение реальных специалистов. Для мелкой правки достаточно одного исполнителя.
